Section 01

What this framework is

The AI Skills Framework is a set of 29 skills — written procedures an AI coding agent follows — that turn "ask an agent to build a feature" into a repeatable process with checkable evidence at every step.

A skill is not a program. It is a Markdown document that tells the agent how to do one job well: how to write requirements, how to break a feature into tickets, how to implement one ticket test-first, how to review a diff. Some skills also ship small Node scripts that check the agent's work deterministically.

The problem it solves is a specific one. Agents are fast and confident, and confidence is not evidence. Left alone, an agent will happily report that a feature is complete because it wrote code that looks complete. This framework makes that harder by keeping four things in separate places:

ArtifactAnswersLives in
SRSWhat should the system do?docs/specifications/
Feature contractWhat is this one feature, exactly?your tracker
Delivery contractWhat is this one ticket, and how is it proved?your tracker
Code & testsWhat does it actually do?the repo

Requirements never live in code comments. Evidence never lives in a commit message. Each artifact has one owner, and changing one on the strength of another requires an explicit decision.

If you read one thing

The framework's core claim is traceability: every ticket points at an acceptance criterion, every acceptance criterion points at a requirement, and every requirement has a stable ID that never gets renumbered. When something is unproved, the framework is designed to say unverified rather than guess.

Section 02

The mental model

Work flows in one direction, and each stage refuses to start until the previous one is complete. That refusal is the point — it is what stops an agent from implementing a ticket nobody has actually specified.

  1. framework-setup — discovers your project and writes its configuration
  2. srs-modeling — the durable requirements baseline
  3. to-spec — one traceable feature contract from the SRS
  4. to-tickets — vertical tickets with an acyclic blocker graph
  5. implement — one ticket, red-green, one fresh context
  6. verify-change — run the ticket's evidence matrix
  7. code-review — Standards, Contract, Security, Evidence

You do not have to use all of it. A small change can go straight to implement with an agreed contract in the conversation. The full chain earns its cost on work that spans several sessions, where the risk is drift rather than typos.

The other skills

The remaining skills are tools you reach for as needed, not stages you pass through:

Section 03

Installing it

Pick the route that matches your agent. All three install the same released skills.

Universal CLI — works with most agents

Run in your project root

npx skills@latest add emipac/skills

The installer asks which skills and which coding agents to configure. You can select a subset.

Claude Code plugin

/plugin marketplace add emipac/skills
/plugin install ai-skills-framework@minic

Codex plugin

codex plugin marketplace add emipac/skills

Then install AI Skills Framework from the Minic marketplace inside Codex.

Installing changes nothing

Installation copies skill files so your agent can read them. It does not edit your project configuration, does not create Git hooks, and cannot block a commit. This matters most for the Change Evaluation Gate: shipping its files never switches it on.

Updating later

Re-run the same install command. Versions are synchronised from package.json, so the CLI, the Claude plugin, and the Codex plugin always report the same release.

Section 04

Configuring a project

Before the lifecycle skills work, the framework needs to know your project: which backend and frontend you use, where your source lives, which commands prove a change is good, and which tracker holds your tickets. That lives in one file at your project root, .agent-framework.yaml.

The intended way to create it is to ask your agent to run framework-setup. It inspects the repository, proposes a configuration, and asks you to confirm anything it could not prove. Underneath, it uses a script you can also run directly:

Discover what the project looks like

node .agents/skills/framework-setup/scripts/configure.mjs --discover
Adjust the path to your install

Commands on this page assume the installer put the skills in .agents/skills. Claude Code installs commonly use .claude/skills instead — check which one exists in your project and swap that one segment. Everything after it is the same.

What ends up in the file

KeyMeaning
schema_version3 or 4. Version 4 is required for the Gate.
backend / frontendWhich profiles are active. none means proved absent; unknown means not yet determined.
source_scopesWhich directories belong to backend, frontend, or both.
verification.commandsThe exact commands that prove a change: format, static analysis, test, smoke, build, e2e.
trackerWhere tickets live — for example local-markdown.
protected_filesFiles the agent must never modify, such as AGENTS.md.
The unknown / none distinction

unknown and none are not the same. none means "we checked, there is no frontend." unknown means "nobody has established this yet." The framework refuses to silently convert one into the other, because that would change which checks run without anyone deciding to.

Section 05

The daily working loop

Once configured, a typical feature runs like this. You are talking to your agent throughout — these are skill names you ask it to use, not shell commands.

1. Write down what the system should do

Ask for srs-modeling. It interviews you, then writes requirements with stable IDs (FR-…), acceptance criteria (AC-…), safeguards (SG-… — things that must never happen), risks, and open questions. Unknowns are recorded as visible questions rather than guessed at.

2. Cut one feature out of it

Ask for to-spec. It produces a feature contract: the problem, the traceability table linking requirements to acceptance criteria, the public seams where behaviour will be observed, and the safeguards that constrain it.

3. Break it into tickets

Ask for to-tickets. Each ticket is a vertical slice — a complete thin behaviour end to end, not "write the database layer." Every ticket carries a Verification Matrix listing the exact commands that will prove it, and a blocker graph that must be acyclic.

4. Implement one ticket

Ask for implement, naming the ticket. It refuses to start if a blocker is incomplete or the ticket lacks traceability. Then it works in red-green cycles: write one failing test at the agreed seam, watch it fail for the right reason, write the minimum code to pass, repeat.

Why red-before-green matters

A test that has never failed proves nothing — it might be asserting something that was already true, or nothing at all. Watching it fail first, for the reason you expect, is what makes the green meaningful. If an agent tells you tests pass but never showed you them failing, you have not been given evidence.

5. Verify and review

verify-change runs the ticket's evidence matrix through the ordered ladder. code-review then examines the diff on four independent axes: Standards, Contract, Security, and Evidence.

The evidence ladder

Eight ordered stages, cheapest and most specific first:

  1. focused
  2. format
  3. static-analysis
  4. affected-tests
  5. smoke
  6. build
  7. browser
  8. broad-tests — regression evidence, not proof the feature works
Section 06

The Change Evaluation Gate

Everything so far depends on an agent choosing to follow a process. The Change Evaluation Gate is the part that does not depend on choice: it is an optional module that evaluates the exact content of every local commit before Git accepts it.

When it is active and you run git commit, the Gate takes an isolated snapshot of precisely what you are committing, runs your configured checks against that snapshot, and either allows the commit or blocks it. The same enforcement applies whether the commit came from you or from an agent.

What makes it different from a normal pre-commit hook

  • It grades a snapshot, not your working directory. If you edit a file while checks are running, the result still describes exactly what you are committing.
  • Absence of evidence is never success. A crash, a timeout, a missing tool, malformed output, or two runs of the same check disagreeing all produce unverified — which blocks, rather than passing.
  • It keeps an append-only evidence record under your Git metadata, with secrets redacted before anything is written.
  • It cannot weaken itself. A commit that changes the Gate's own policy is evaluated against the previous trusted policy as well as the new one.

The four outcomes

OutcomeMeaningBlocks?
passedThe check ran and succeeded.No
failedThe check ran and failed.Yes, if required
unverifiedThe check could not be trusted to have run correctly.Yes, if required
not-applicableThe check does not apply to this change.No

required and advisory are policy settings you choose, not outcomes. An advisory check never blocks, and an advisory pass never compensates for a required failure.

Section 07

Installed, configured, activated

These three words are the most important thing to understand about the Gate, and they are easy to conflate. Each is a separate, deliberate step. None implies the next.

installed

The Gate's files exist where your agent can read them. Your repository is untouched. No hook, no config change, no effect on commits.

configured

Your .agent-framework.yaml holds an approved evaluation_gate policy. Still no hook. Commits are still unaffected.

activated

This clone has a receipt and a registered Git hook. Only now does anything block a commit.

Configuration is shared — it lives in a file you commit, so your whole team sees the same policy. Activation is clone-local — it applies to your machine only. Cloning a repository whose policy is configured does not activate anything for you; you activate deliberately, or you do not.

Why separate them

Because installing a tool should never quietly start blocking your colleagues' commits. A teammate can pull a branch that configures Gate policy and notice no change in behaviour at all until they choose to activate.

Section 08

Turning the Gate on

Step 1 — Install the module

Select change-evaluation-gate during installation. It is independently selectable; if you install the whole plugin instead, its files ship dormant.

Step 2 — Move to schema v4

Gate policy exists only in schema version 4. If your .agent-framework.yaml says schema_version: 3, migrate first:

Migration runs in four steps and writes nothing until the last one. Do not try to guess the mapping file up front — let the tool tell you what it needs.

You create these files yourself

mapping.json and policy.json are files you write. Nothing generates them, and neither exists until you create it — pointing --mapping or --policy at a file that is not there fails with ENOENT: no such file or directory.

Put them wherever you run the command, usually your project root. They are one-shot inputs: once the change is confirmed nothing reads them again, because the real state lives in .agent-framework.yaml. Delete them afterwards or keep them as a record of your decisions — but there is no reason to commit them.

1 — Ask with an empty mapping

Here, and only here, an empty file is the right starting point: it is what makes the tool report back what it cannot work out on its own. 

echo '{}' > mapping.json
node .agents/skills/framework-setup/scripts/configure.mjs --migrate-v4 --mapping mapping.json

2 — Read exactly what it cannot prove

{
  "status": "requires-mapping",
  "ambiguities": [
    { "path": "backend", "value": "unknown", "required": ["profile"] },
    { "path": "verification.commands.test.both[0]", "value": "npm run test",
      "required": ["timeout_seconds"] }
  ]
}

Nothing has been written. It asks only about what it genuinely cannot determine — here it already worked out the runner and arguments for npm run test by itself and wants only a timeout.

Do not paste this output into mapping.json

This is a list of questions, not a form. The mapping file has a different shape, and the two are inverted: the report lists a path and says which field is missing; the mapping uses that path as a key and supplies the field.

In particular, "required": ["timeout_seconds"] means "this command has no timeout yet". It is not a slot to write 30 into. And status, fromVersion, previewHash and ambiguities are not mapping sections — only profiles and commands exist, so leaving them in fails with Unsupported migration mapping section.

3 — Answer those exact paths

Each ambiguity's path becomes a key, and you supply the field it said was missing. A real Laravel project with a frontend usually looks like this: 

{
  "commands": {
    "verification.commands.format.backend[0]":           { "timeout_seconds": 30 },
    "verification.commands.format.frontend[0]":          { "timeout_seconds": 30 },
    "verification.commands.static_analysis.backend[0]":  { "timeout_seconds": 60 },
    "verification.commands.static_analysis.frontend[0]": { "timeout_seconds": 30 },
    "verification.commands.test.backend[0]":             { "timeout_seconds": 600 },
    "verification.commands.build.frontend[0]":           { "timeout_seconds": 300 }
  }
}

Only two sections exist: profiles and commands. Add profiles only if a profile was reported ambiguous, which happens when its schema v3 value was unknown: 

{
  "profiles": { "backend": "laravel" },
  "commands": { }
}

Per command you may set runner (one of composer-bin, php-script, package-script, repository-script), args, working_directory, timeout_seconds, and allowed_environment. Usually only the timeout is needed — the tool works out the runner and splits the arguments itself.

Choose timeouts generously

A check that exceeds its timeout reports unverified, which blocks — absence of evidence is never success. A full test suite or a cold build is easily slower than it feels. Start high, then tighten once you have seen real durations; these are ordinary configuration values you can edit any time.

Re-run the command from step 1. You now get "status": "ready", a previewHash, and the complete proposed configuration to read. Still nothing written.

4 — Confirm that exact preview

node .agents/skills/framework-setup/scripts/configure.mjs \
  --migrate-v4 --mapping mapping.json --confirm PASTE_THE_PREVIEWHASH_HERE

Only now does .agent-framework.yaml change. The hash is bound to the exact preview you were shown, so if the file changes underneath you the confirmation stops matching and nothing is written — which is the entire point of it.

Migration never configures or activates the Gate; it only makes configuration possible. Schema v3 stays readable throughout 0.x.

Step 3 — Configure the policy

node .agents/skills/framework-setup/scripts/configure.mjs \
  --configure-gate --policy policy.json

Like migration, this previews first and returns a hash you confirm with --confirm. Nothing is written until you do.

The policy has exactly five parts, and nothing else:

PartWhat you decide
Check identitiesWhich checks are required and which are advisory.
Total budgetHow long a whole evaluation may take.
Bypass policyWhether an escape hatch exists at all, and what it demands.
Execution policyPer-check timeouts, and which advisory checks may be skipped when the budget runs short.
Evidence policyRetention limits, never above the built-in ceilings.

Notice what is not here: commands. The Gate references check identities that verify-change already owns. There is exactly one place a command is defined, so the two can never disagree.

A policy that works

Do not start this one empty

policy.json is another file you create, but the habit migration teaches does not carry over. An empty {} here does not produce a helpful report — it stops at Missing Gate policy subcontract: checks and tells you nothing about the other four. Write the whole file up front.

Start from this. Configuration activates nothing, so an empty required list is harmless — and it lets you add identities once you have confirmed what your checks are really called. 

cat > policy.json <<'JSON'
{
  "checks":    { "required": [], "advisory": [] },
  "budget":    { "total_seconds": 900 },
  "bypass":    { "enabled": false },
  "execution": { },
  "evidence":  { }
}
JSON

This starter is configuration-valid, but it does not make any check blocking. Before activation, decide which confirmed Verification identities are required and which are advisory, then preview the resulting policy again. An identity not listed as required remains advisory.

Four things that will trip you up

1 — All five are mandatory; bypass is explicit

You cannot omit bypass because you do not want bypass. Leaving it out fails with Missing Gate policy subcontract: bypass. Write {"enabled": false} when bypass is disabled. The same policy validator used by the Gate runtime checks setup previews, so an enabled bypass also needs its commit-visible marker. Empty execution and evidence objects are valid when no additional policy is needed.

2 — budget takes exactly one key

Adding anything beside total_seconds fails with "Gate budget policy must contain a positive total_seconds integer" — which is misleading, because your integer was fine. The extra key was the problem. Per-check timeouts belong in execution, not here.

3 — Some field names are refused anywhere

Writing "execution": {"commands": {…}} is the obvious move and it is rejected: Gate policy cannot own verification or activation field: commands. These names are refused at any nesting depth — command, commands, args, runner, executable, working_directory, allowed_environment, evidence_category, source_scope, version, profile, profiles, capabilities, client, hook, trust, receipt, activation, activated.

That is command ownership enforced structurally rather than by convention. Name your keys around it — "execution": {"timeouts": {"my-check": 60}} is accepted, and an innocent "version": 1 inside your evidence policy is not.

4 — Check identities are not verified here

A policy naming a check that does not exist is accepted without complaint. A typo will not surface until evaluation, when the check you meant quietly is not the one running. Add identities only after you have confirmed the exact names your verification configuration uses.

Configuration is one-shot. Running it again fails with The Gate is already configured — to change policy afterwards, edit the evaluation_gate block in .agent-framework.yaml directly, or remove it and configure again. The block lands as inline JSON, one line per subcontract, which is valid YAML if not especially pretty.

Step 4 — Activate on your machine

There is no gate activate command yet

In release 0.9.0 the Gate is agent-operated. There is no bin entry and no CLI: activation, status, repair, update, and removal exist as library functions that your agent calls by following the change-evaluation-gate skill. Ask your agent to use that skill rather than looking for a command to type. A typed gate command is a reasonable future addition, but it does not exist today.

Activation runs as one transaction, in a fixed order, and enables Git last:

  1. repository-identity — confirm which clone this is
  2. preview — show the exact changes and commands
  3. consent — you approve that specific preview
  4. runner-resolution — resolve each command to a real executable
  5. trust — client-controlled, never granted on your behalf
  6. hook-chain-validation — inspect existing hooks without touching them
  7. self-test — prove the machinery works before relying on it
  8. receipt — record what was pinned
  9. git-enablement — only now can a commit be blocked

If any step fails, everything already done is unwound and your clone is left configured — never half-activated. Existing hooks are never overwritten: the Gate composes into a hook chain, or refuses and tells you why.

Section 09

What happens at a commit

You run git commit. Before Git accepts it:

  1. The Gate materialises an isolated snapshot of exactly what you are committing.
  2. It resolves which checks apply, in ladder order.
  3. It runs them against the snapshot, never against your live files.
  4. It applies your policy: required failures and unverifieds deny; advisory ones do not.
  5. It writes an evidence record and returns a decision.

A denial tells you which check failed and why, without you having to dig through logs. Your working directory is never modified by an evaluation — checks that would rewrite your code are rejected at commit time and belong to a separate explicit fix operation.

If you genuinely need to commit anyway

Bypass is optional — a project can disable it entirely. Where it is enabled it is deliberately awkward: one-shot, bound to that exact snapshot, requires a written reason and any reference your policy demands, and emits a commit-visible marker. It returns bypassed, never passed, and the failures it stepped over stay recorded.

Evidence limits

Records are bounded so they cannot fill your disk: 32 KiB inline per attempt, 4 MiB per output blob, 32 MiB of blobs per evaluation. Projects may lower these, never raise them. Truncation keeps the beginning and end of output and records how much was dropped. Nothing is ever deleted automatically — pruning is manual and preview-bound.

Section 10

Status, repair, turning it off

All of these are agent-driven through the Gate skill, for the reason given in Section 08.

OperationWhat it does
statusReports healthy, degraded, or broken. Repairs nothing and writes nothing — observation never mutates.
repairRestores drifted Gate-owned registrations, only after you confirm a preview.
updateSwitches to a newer Gate release atomically. Installing a newer version only makes a candidate available; nothing changes until you update deliberately.
deactivateRemoves the hook and receipt. Keeps your configuration and all historical evidence.
uninstallRemoves project-installed assets. Requires deactivation first.
cleanupRemoves only Gate keys from .agent-framework.yaml. Never deletes the file.

Every removal is conservative: it touches only unchanged Gate-owned state, and refuses the whole operation rather than half-doing it. Anything that drifted is reported and left exactly where it is.

Section 11

Limits you should know

These are real constraints in 0.9.0, not disclaimers. Plan around them.

It is not tamper-proof

Trust boundary

The Gate is a cooperative local process running with your own permissions. Anyone can pass --no-verify, delete the hook, or edit the evidence files. It does not resist the machine owner and is not a sandbox. It is reproducible pre-commit enforcement for a trusted developer machine — not a substitute for CI, and not protection against hostile code.

Desktop client support is narrow

Desktop editors can show preflight feedback before you commit, but they never authorise anything — only the Git integration does. Support is claimed only where a real client has actually been tested:

SurfaceStatusWhy
Cursor 3.15.6supportedPassed the full baseline driven by a real client invocation.
Claude Code DesktopexperimentalNo client-driven baseline run yet.
Codex DesktopexperimentalNo client-driven baseline run yet.
GitexperimentalAuthoritative regardless of tier; tier reflects baseline provenance.

One environment is claimed

The release records exactly one tested environment: macOS 26.6.1, arm64, Node v24.6.0, git 2.51.0. Every other combination is unverified — not refused. Running the portability matrix on another machine is how that machine earns a claim. This is deliberate: tested versions are an evidence snapshot, never a permanent allowlist.

Two risks stay open

  • Slow checks encourage bypass. If your required checks are slow, people route around them. Keep the commit gate fast and put slow suites in CI.
  • Flaky checks block delivery. Two runs of one unchanged check that disagree produce unverified and block, by design. Fix the flake rather than retrying it away.
Section 12

Glossary

Skill
A Markdown procedure an agent follows. Some ship deterministic Node scripts alongside.
SRS
Software Requirements Specification — the durable record of intended behaviour, with stable IDs.
Stable ID
An identifier such as FR-EVAL-001 that is never renumbered or reused, so links stay valid forever.
Safeguard
A negative-space rule: something that must never happen, plus what to do if it does.
Vertical slice
A thin complete behaviour end to end, rather than one horizontal layer.
Evidence ladder
The eight ordered check stages, cheapest and most specific first.
Snapshot
An isolated copy of exactly the content being committed, so results cannot be confused with unstaged edits.
unverified
The check could not be trusted to have run correctly. Treated as blocking, never as a pass.
Receipt
The clone-local record proving what was activated and what it pinned.
Preflight
Non-authoritative early feedback from a desktop client. Never grants or denies a commit.
