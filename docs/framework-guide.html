Section 01

What this framework is

The AI Skills Framework is a set of 29 skills — written procedures an AI coding agent follows — that turn "ask an agent to build a feature" into a repeatable process with checkable evidence at every step.

A skill is not a program. It is a Markdown document that tells the agent how to do one job well: how to write requirements, how to break a feature into tickets, how to implement one ticket test-first, how to review a diff. Some skills also ship small Node scripts that check the agent's work deterministically.

The problem it solves is a specific one. Agents are fast and confident, and confidence is not evidence. Left alone, an agent will happily report that a feature is complete because it wrote code that looks complete. This framework makes that harder by keeping four things in separate places:

ArtifactAnswersLives in
SRSWhat should the system do?docs/specifications/
Feature contractWhat is this one feature, exactly?your tracker
Delivery contractWhat is this one ticket, and how is it proved?your tracker
Code & testsWhat does it actually do?the repo

Requirements never live in code comments. Evidence never lives in a commit message. Each artifact has one owner, and changing one on the strength of another requires an explicit decision.

If you read one thing

The framework's core claim is traceability: every ticket points at an acceptance criterion, every acceptance criterion points at a requirement, and every requirement has a stable ID that never gets renumbered. When something is unproved, the framework is designed to say unverified rather than guess.

Section 02

The mental model

Work flows in one direction, and each stage refuses to start until the previous one is complete. That refusal is the point — it is what stops an agent from implementing a ticket nobody has actually specified.

  1. framework-setup — discovers your project and writes its configuration
  2. srs-modeling — the durable requirements baseline
  3. to-spec — one traceable feature contract from the SRS
  4. to-tickets — vertical tickets with an acyclic blocker graph
  5. implement — one ticket, red-green, one fresh context
  6. verify-change — run the ticket's evidence matrix
  7. code-review — Standards, Contract, Security, Evidence

You do not have to use all of it. A small change can go straight to implement with an agreed contract in the conversation. The full chain earns its cost on work that spans several sessions, where the risk is drift rather than typos.

The other skills

The remaining skills are tools you reach for as needed, not stages you pass through:

Section 03

Installing it

Pick the route that matches your agent. All three install the same released skills.

Universal CLI — works with most agents

Run in your project root

npx skills@latest add emipac/skills

The installer asks which skills and which coding agents to configure. You can select a subset.

Claude Code plugin

/plugin marketplace add emipac/skills
/plugin install ai-skills-framework@minic

Codex plugin

codex plugin marketplace add emipac/skills

Then install AI Skills Framework from the Minic marketplace inside Codex.

Installing changes nothing

Installation copies skill files so your agent can read them. It does not edit your project configuration, does not create Git hooks, and cannot block a commit. This matters most for the Change Evaluation Gate: shipping its files never switches it on.

Updating later

Re-run the same install command. Versions are synchronised from package.json, so the CLI, the Claude plugin, and the Codex plugin always report the same release.

Section 04

Configuring a project

Before the lifecycle skills work, the framework needs to know your project: which backend and frontend you use, where your source lives, which commands prove a change is good, and which tracker holds your tickets. That lives in one file at your project root, .agent-framework.yaml.

The intended way to create it is to ask your agent to run framework-setup. It inspects the repository, proposes a configuration, and asks you to confirm anything it could not prove. Underneath, it uses a script you can also run directly:

Discover what the project looks like

node .agents/skills/framework-setup/scripts/configure.mjs --discover
Adjust the path to your install

Commands on this page assume the installer put the skills in .agents/skills. Claude Code installs commonly use .claude/skills instead — check which one exists in your project and swap that one segment. Everything after it is the same.

What ends up in the file

Ten top-level keys, one of them optional. In short: which profiles are active (backend, frontend), where their code lives (source_scopes), the exact commands that prove a change (verification.commands), where tickets and documents live (tracker, artifacts, history), which files an agent must never touch (protected_files), and — once you configure the Gate — the evaluation_gate policy.

Section 05 is the full reference, with every key, every legal value, and who decides it. Read it before you hand-edit this file, which you will end up doing.

The unknown / none distinction

unknown and none are not the same. none means "we checked, there is no frontend." unknown means "nobody has established this yet." The framework refuses to silently convert one into the other, because that would change which checks run without anyone deciding to.

Section 05

The configuration file, in full

.agent-framework.yaml has two readers. The lifecycle skills read it to know your project; the Gate reads it to know what to enforce. framework-setup writes it, but every project ends up editing it by hand — to add a dependency root, raise a timeout, declare a secret — so this is the reference for doing that safely.

The authoritative shape is skills/framework-setup/references/agent-framework.schema.json, a JSON Schema you can validate against. Both schema v3 and v4 are legal; v4 is required for the Gate and is what this section documents.

Why the inline JSON

The Gate block is written as one line of JSON per subcontract. That is valid YAML, it is what --configure-gate emits, and it keeps each subcontract a single unit you replace whole rather than a block you can half-edit. You may reformat it as ordinary YAML if you prefer; only the parsed value matters, and any edit needs a re-pin either way (Section 12).

unknown is not none, and null is neither

none means "we checked; there is no frontend." unknown means "nobody has established this yet" — it stays active and conservative, so its checks still run. A null path, or an empty list, is an explicit unresolved value: a skill that needs it must ask rather than invent one. Nothing in the framework silently converts between these, because each conversion changes which checks run.

verification.commands — the Command descriptor

Commands are grouped by category (format, static_analysis, test, smoke, build, e2e), then by scope (backend, frontend, both — all three keys always present, empty lists allowed). In v4 each entry is an OS-independent descriptor with exactly these seven fields, all required:

FieldLegal valuesNotes

Adding a flag to a tool — a memory limit, an extra path — is an edit to args here, and nowhere else. There is exactly one place a command is defined, which is why Gate policy names check identities rather than commands.

evaluation_gate — the five subcontracts

All five are mandatory once the key exists. Here is the part that surprises people: the schema constrains only checks and budget. The other three are open maps — any key except a banned name, any JSON value — and the Gate, not the schema, decides what it reads out of them. So a misspelled key in execution or evidence validates cleanly and does nothing.

Names the Gate block may never use, at any depth

activation, activated, allowed_environment, args, capabilities, client, command, commands, evidence_category, executable, hook, profile, profiles, receipt, runner, source_scope, trust, version, working_directory.

That is command ownership enforced structurally: Gate policy cannot grow a second place where a command lives. An innocent "version": 1 inside your evidence policy is rejected for the same reason as a deliberate "commands". Section 09 has the rest of the hand-editing refusals.

Every edit in this section needs a re-pin

On an activated clone, changing any of this has no effect until you re-pin it with git gate sync — and until you do, commits are denied with integrity-drift, and git gate status reports broken and names that re-pin. Section 12.

Section 06

The daily working loop

Once configured, a typical feature runs like this. You are talking to your agent throughout — these are skill names you ask it to use, not shell commands.

1. Write down what the system should do

Ask for srs-modeling. It interviews you, then writes requirements with stable IDs (FR-…), acceptance criteria (AC-…), safeguards (SG-… — things that must never happen), risks, and open questions. Unknowns are recorded as visible questions rather than guessed at.

2. Cut one feature out of it

Ask for to-spec. It produces a feature contract: the problem, the traceability table linking requirements to acceptance criteria, the public seams where behaviour will be observed, and the safeguards that constrain it.

3. Break it into tickets

Ask for to-tickets. Each ticket is a vertical slice — a complete thin behaviour end to end, not "write the database layer." Every ticket carries a Verification Matrix listing the exact commands that will prove it, and a blocker graph that must be acyclic.

4. Implement one ticket

Ask for implement, naming the ticket. It refuses to start if a blocker is incomplete or the ticket lacks traceability. Then it works in red-green cycles: write one failing test at the agreed seam, watch it fail for the right reason, write the minimum code to pass, repeat.

Why red-before-green matters

A test that has never failed proves nothing — it might be asserting something that was already true, or nothing at all. Watching it fail first, for the reason you expect, is what makes the green meaningful. If an agent tells you tests pass but never showed you them failing, you have not been given evidence.

5. Verify and review

verify-change runs the ticket's evidence matrix through the ordered ladder. code-review then examines the diff on four independent axes: Standards, Contract, Security, and Evidence.

The evidence ladder

Eight ordered stages, cheapest and most specific first:

  1. focused
  2. format
  3. static-analysis
  4. affected-tests
  5. smoke
  6. build
  7. browser
  8. broad-tests — regression evidence, not proof the feature works
Section 07

The Change Evaluation Gate

Everything so far depends on an agent choosing to follow a process. The Change Evaluation Gate is the part that does not depend on choice: it is an optional module that evaluates the exact content of every local commit before Git accepts it.

When it is active and you run git commit, the Gate takes an isolated snapshot of precisely what you are committing, runs your configured checks against that snapshot, and either allows the commit or blocks it. The same enforcement applies whether the commit came from you or from an agent.

What makes it different from a normal pre-commit hook

  • It grades a snapshot, not your working directory. If you edit a file while checks are running, the result still describes exactly what you are committing.
  • Absence of evidence is never success. A crash, a timeout, a missing tool, malformed output, or two runs of the same check disagreeing all produce unverified — which blocks, rather than passing.
  • It keeps an append-only evidence record under your Git metadata, with secrets redacted before anything is written.
  • It cannot weaken itself. A commit that changes the Gate's own policy is evaluated against the previous trusted policy as well as the new one.

The four outcomes

OutcomeMeaningBlocks?
passedThe check ran and succeeded.No
failedThe check ran and failed.Yes, if required
unverifiedThe check could not be trusted to have run correctly.Yes, if required
not-applicableThe check does not apply to this change.No

required and advisory are policy settings you choose, not outcomes. An advisory check never blocks, and an advisory pass never compensates for a required failure.

Section 08

Installed, configured, activated

These three words are the most important thing to understand about the Gate, and they are easy to conflate. Each is a separate, deliberate step. None implies the next.

installed

The Gate's files exist where your agent can read them. Your repository is untouched. No hook, no config change, no effect on commits.

configured

Your .agent-framework.yaml holds an approved evaluation_gate policy. Still no hook. Commits are still unaffected.

activated

This clone has a receipt and a registered Git hook. Only now does anything block a commit.

Configuration is shared — it lives in a file you commit, so your whole team sees the same policy. Activation is clone-local — it applies to your machine only. Cloning a repository whose policy is configured does not activate anything for you; you activate deliberately, or you do not.

Why separate them

Because installing a tool should never quietly start blocking your colleagues' commits. A teammate can pull a branch that configures Gate policy and notice no change in behaviour at all until they choose to activate.

Section 09

Turning the Gate on

Four steps, in order. Every heading below carries a badge saying who does the work, because that is the single most useful thing to know before you start:

tool-derived

A command produces this from facts your project already proves. You run the command and read the result; you do not author the content.

your decision

Nothing can derive this. You type it, or you choose it. Where a draft leaves a null, that null marks exactly this.

two invocations

A command that previews first and writes nothing, then performs exactly that preview when you run it again naming the token it printed. You can type both, and so can an agent following the change-evaluation-gate skill.

Steps 1 and 2 are mostly mechanical. Step 3 is where your real decisions live. Step 4 is the only one that changes your machine rather than your repository.

Step 1 — Install the module your decision

Select change-evaluation-gate during installation. It is independently selectable; if you install the whole plugin instead, its files ship dormant.

Step 2 — Move to schema v4 tool-derived

Gate policy exists only in schema version 4. If your .agent-framework.yaml says schema_version: 3, migrate first:

Migration runs in four steps and writes nothing until the last one. Do not try to guess the mapping file up front — let the tool tell you what it needs.

You create these files yourself

mapping.json and policy.json are files you own. Neither exists until you create it — pointing --mapping or --policy at a file that is not there fails with ENOENT: no such file or directory. You can start each one from a derived draft (--draft-mapping and --draft-policy, both shown below), but a draft is a starting point: it leaves a null wherever the framework has proved nothing, and those are yours to answer.

Put them wherever you run the command, usually your project root. They are one-shot inputs: once the change is confirmed nothing reads them again, because the real state lives in .agent-framework.yaml. Delete them afterwards or keep them as a record of your decisions — but there is no reason to commit them.

1 — Ask with an empty mapping tool-derived

Here, and only here, an empty file is the right starting point: it is what makes the tool report back what it cannot work out on its own. 

echo '{}' > mapping.json
node .agents/skills/framework-setup/scripts/configure.mjs --migrate-v4 --mapping mapping.json

2 — Read exactly what it cannot prove tool-derived

{
  "status": "requires-mapping",
  "ambiguities": [
    { "path": "backend", "value": "unknown", "required": ["profile"] },
    { "path": "verification.commands.test.both[0]", "value": "npm run test",
      "required": ["timeout_seconds"] }
  ]
}

Nothing has been written. It asks only about what it genuinely cannot determine — here it already worked out the runner and arguments for npm run test by itself and wants only a timeout.

Do not paste this output into mapping.json

This is a list of questions, not a form. The mapping file has a different shape, and the two are inverted: the report lists a path and says which field is missing; the mapping uses that path as a key and supplies the field.

In particular, "required": ["timeout_seconds"] means "this command has no timeout yet". It is not a slot to write 30 into. And status, fromVersion, previewHash and ambiguities are not mapping sections — only profiles and commands exist, so leaving them in fails with Unsupported migration mapping section.

You do not have to perform that inversion by hand. --draft-mapping emits a mapping already keyed by these exact paths, with a null where each answer goes: 

node .agents/skills/framework-setup/scripts/configure.mjs \
  --draft-mapping --out mapping.json

It writes nothing else, refuses to overwrite an existing mapping.json, and prints the draft to stdout when you omit --out. Replace each null with a proved value; a mapping still containing one is refused rather than filled in for you.

3 — Answer those exact paths your decision

Each ambiguity's path becomes a key, and you supply the field it said was missing. A real Laravel project with a frontend usually looks like this: 

{
  "commands": {
    "verification.commands.format.backend[0]":           { "timeout_seconds": 30 },
    "verification.commands.format.frontend[0]":          { "timeout_seconds": 30 },
    "verification.commands.static_analysis.backend[0]":  { "timeout_seconds": 60 },
    "verification.commands.static_analysis.frontend[0]": { "timeout_seconds": 30 },
    "verification.commands.test.backend[0]":             { "timeout_seconds": 600 },
    "verification.commands.build.frontend[0]":           { "timeout_seconds": 300 }
  }
}

Only two sections exist: profiles and commands. Add profiles only if a profile was reported ambiguous, which happens when its schema v3 value was unknown: 

{
  "profiles": { "backend": "laravel" },
  "commands": { }
}

Per command you may set runner (one of composer-bin, php-script, package-script, repository-script), args, working_directory, timeout_seconds, and allowed_environment. Usually only the timeout is needed — the tool works out the runner and splits the arguments itself.

Choose timeouts generously

A check that exceeds its timeout reports unverified, which blocks — absence of evidence is never success. A full test suite or a cold build is easily slower than it feels. Start high, then tighten once you have seen real durations; these are ordinary configuration values you can edit any time.

Re-run the command from step 1. You now get "status": "ready", a previewHash, and the complete proposed configuration to read. Still nothing written.

4 — Confirm that exact preview your decision

node .agents/skills/framework-setup/scripts/configure.mjs \
  --migrate-v4 --mapping mapping.json --confirm PASTE_THE_PREVIEWHASH_HERE

Only now does .agent-framework.yaml change. The hash is bound to the exact preview you were shown, so if the file changes underneath you the confirmation stops matching and nothing is written — which is the entire point of it.

Migration never configures or activates the Gate; it only makes configuration possible. Schema v3 stays readable throughout 0.x.

Step 3 — Configure the policy your decision

This is the step with real choices in it, so it is worth knowing up front which parts the tooling can work out and which parts are genuinely yours. The policy has exactly five subcontracts and nothing else:

SubcontractWhat it decidesWho writes it
checks Which checks are required and which are advisory. tool-derived — you review
budget How long a whole evaluation may take. tool-derived — when your timeouts are proved
bypass Whether an escape hatch exists at all, and what it demands. your decision
execution Which advisory checks may be skipped when the budget runs short. your decision
evidence Retention limits, never above the built-in ceilings. your decision

Notice what is not here: commands. The Gate references check identities that verify-change already owns. There is exactly one place a command is defined, so the two can never disagree.

The four sub-steps below follow the same rhythm as Step 2 — draft, decide, preview, confirm — and nothing is written until the last one.

1 — Draft the policy tool-derived

Do not hand-write this file. --draft-policy reads your project's own schema v4 configuration and derives the check identities the activated hook will actually bind, each one bound required or advisory from the matching provider's declared default: 

node .agents/skills/framework-setup/scripts/configure.mjs \
  --draft-policy --out policy.json

For a project with format, test, and build commands configured, that produces: 

{
  "checks": {
    "required": ["configuration.format.formatter", "configuration.broad-tests.test"],
    "advisory": ["configuration.build.build"]
  },
  "budget":    { "total_seconds": 930 },
  "bypass":    { "enabled": false, "marker": null },
  "execution": { "budget_skippable": [] },
  "evidence":  { }
}

The two checks lists and budget.total_seconds are derived — the identities from your configured commands, the bindings from the provider, the budget as the sum of the timeouts you already proved during migration. The last three subcontracts are safe defaults, not derived answers: the draft always writes bypass disabled, nothing skippable, and no retention override. Changing any of them is entirely your call.

It writes nothing else, prints to stdout when you omit --out, and refuses to overwrite an existing policy.json. It also refuses outright — rather than guessing — if your project has not migrated to schema v4 or has no commands configured, because there is nothing to derive an identity from yet.

2 — Decide what the draft could not your decision

The draft is a proposal, not a decision. Work down this list before you configure it:

Look atAnd decide
checks.required Whether each one is genuinely worth blocking a commit for. Anything you demote belongs in advisory; an identity in neither list simply does not participate.
budget.total_seconds Whether that total is tolerable at every commit. If it reads null, your configuration proved no timeouts and you must supply a positive integer yourself.
bypass Whether an escape hatch should exist. The draft says no. To enable it, set "enabled": true and give it a commit-visible marker string — an enabled bypass without one is refused.
execution.budget_skippable Which advisory checks may be dropped when time runs short. It may never name anything in required.
execution.dependency_roots Repository-relative directories your checks need but Git does not track — vendor, node_modules, and anything a build step generates. They are provided beside the snapshot, and are never graded.
execution.dependency_provisioning How those directories are provided: link (the default — a symbolic link to your own installation, provided instantly) or copy (a real directory beside the snapshot). Declare copy only for the roots whose tooling resolves a path to its realpath. Write one word to apply it to every root, or a map to choose per root — {"vendor": "copy"} — where anything the map does not name stays link. It is never detected for you.
evidence Whether to lower any retention ceiling. Leaving it empty keeps the built-in bounds, which is usually right.
evidence.sensitive_inputs The environment variable names whose values your checks might print — APP_KEY, a mail password, an API token. Each declared value is removed from everything the Gate stores before it is written, in every form it recognizes. Names only: a value here is refused. Declaring one changes the configuration identity, so re-run gate activate afterwards. An approved name is also handed to every check, regardless of its allowed_environment.
evidence.environment_files Repository-relative, git-ignored files in NAME=value form — .env — the Gate may resolve a declared name from when your own shell does not export it. Only the declared names are read from a file; nothing else in it is read, copied, or reported, and a tracked file is refused. Your shell's value always wins over the file. The Laravel setup draft declares APP_KEY and .env for you.
Untracked does not mean unnecessary

A snapshot holds source files, not installed ones. Whatever your .gitignore excludes is never in it — so a tool that reads an installed dependency, or an import path some build step generates, finds nothing there unless you name its directory in execution.dependency_roots. This is the single most likely reason a check that passes in your terminal does not pass in the Gate.

The two snapshots hold different things

"The snapshot" is two slightly different trees, and the difference matters more than it sounds:

Taken atHolds
git commit Exactly the tracked content you are committing — the index, written out with git checkout-index. Nothing untracked, ever.
A desktop preflight What a person looking at the clone would see: tracked files plus every untracked file your .gitignore does not exclude, minus deletions.

So an untracked file you never think about is inside the preflight capture. Usually that is what you want — it is how a file the agent has just written gets graded before it is staged. It also means anything untracked and un-ignored is the Gate's problem too.

Gitignore your installed skills — 0.8.0 defect

Several installers place agent skills in your project as symbolic links to directories — .claude/skills/<skill> pointing at a shared checkout is the common shape. Those links are untracked, and unless you ignore them they are enumerated into the preflight capture by the rule above. Materialising one reads the link, follows it to a directory, and fails: 

Preflight (not a commit decision): unverified.
Diagnostics:
- snapshot-mismatch: The exact snapshot could not be materialized: EISDIR: illegal operation on a directory, read

The capture is all-or-nothing, so one such link makes every preflight unverified — no checks run, and the message names no path. Commits are unaffected, because the commit snapshot is tracked-only. A clone in this state looks activated, healthy and quiet, and is silently telling you nothing.

Ignore the install directories your agents use

printf '/.claude\n/.agents\n/.cursor\n' >> .gitignore

Ignore only the ones your project actually has, and check first whether any of them holds something you meant to commit. If you would rather not change a shared file, the same lines in .git/info/exclude are clone-local and work identically. No re-pin is needed — ignore rules are not pinned by the receipt.

This is a defect, not a design: a snapshot has no stated policy for a symlink, and the capture should not die on one. Until it has one, ignoring the directories is the fix.

If your tool asks where a file is

A dependency root is linked by default, and a link is reachable — which is all most tools need. A tool that resolves a path to its realpath needs more: it follows the link out of the snapshot and concludes your project lives in your own clone, not in the tree it is grading. PHP's __DIR__ inside an autoloader does this, so a test runner derives the wrong project root; a TypeScript import resolver does it, so your own aliased imports are classified as external and an import-order rule fails code that is correct. If your formatter, static analysis, or tests fail only under the Gate and pass by hand, declare copy for that root.

Declare it per root, not for everything. A scalar "dependency_provisioning": "copy" copies every declared root; a map copies only the ones you name: 

execution: {"dependency_roots": ["node_modules", "vendor", "resources/js/actions"],
            "dependency_provisioning": {"vendor": "copy", "resources/js/actions": "copy"}}

A key naming a directory that is not in dependency_roots is refused by name, never ignored. A copy that cannot be performed is reported dependency-root-unavailable and never quietly served as a link.

What it costs depends on your filesystem, and the Gate finds out by measuring rather than by asking which system you are on. Each capture that copies anything writes one 8 MiB probe, asks the platform's own copy program to clone it, and reads the volume's free space before and after. Where the clone really happened — APFS, Btrfs, XFS with reflinks, ReFS — the roots are shared rather than duplicated and cost close to nothing in disk. Where it did not, the bytes are written and a tree of thirty-four thousand files costs roughly ten seconds to provide, two to reclaim, and 373 MiB per evaluation. Copying only the roots that need it is what keeps that bill small on the machines that have to pay it.

Only require what your project can run

A check whose tool is not present does not get skipped — it resolves to unverified, and an unverified required check blocks. The drafter only ever proposes identities your configuration actually proves, so this trap belongs to hand-written policies. It still pays to sanity-check that every required command really runs on a clean clone.

node .agents/skills/framework-setup/scripts/configure.mjs \
  --configure-gate --policy policy.json

Exactly like migration: this returns the complete proposed configuration and a previewHash, and writes nothing.

You do not need any of this if you used --draft-policy. It matters only when you write or edit policy.json by hand, and it explains why hand-writing is discouraged.

The identity the commit hook binds is not the one the provider declares. The activated hook derives its checks from your own verification.commands and names them configuration.<stage>.<capability>:

If you edit policy.json by hand

These five refusals are what you will hit. The drafter avoids all of them, so this is troubleshooting rather than instruction.

1 — All five are mandatory; bypass is explicit

You cannot omit bypass because you do not want bypass. Leaving it out fails with Missing Gate policy subcontract: bypass. Write {"enabled": false} when bypass is disabled. An empty {} policy is no help either — it stops at Missing Gate policy subcontract: checks and tells you nothing about the other four.

2 — budget takes exactly one key

Adding anything beside total_seconds fails with "Gate budget policy must contain a positive total_seconds integer" — which is misleading, because your integer was fine. The extra key was the problem. Per-check timeouts belong in verification.commands, not here.

3 — Some field names are refused anywhere

Writing "execution": {"commands": {…}} is the obvious move and it is rejected: Gate policy cannot own verification or activation field: commands. These names are refused at any nesting depth — command, commands, args, runner, executable, working_directory, allowed_environment, evidence_category, source_scope, version, profile, profiles, capabilities, client, hook, trust, receipt, activation, activated.

That is command ownership enforced structurally rather than by convention. Name your keys around it — "execution": {"timeouts": {"my-check": 60}} is accepted, and an innocent "version": 1 inside your evidence policy is not.

4 — Check identities are never validated

The entire rule is "a non-empty string". No spelling check, no separator rule, no cross-check against your project. A policy naming a check that does not exist is accepted without complaint, and the mistake does not surface until evaluation — as a required check that quietly is not running. This single fact is why the drafter exists.

5 — Required work is never skipped for the budget

execution.budget_skippable may not name anything you listed in required; the validator rejects that combination outright. Skipping to fit a time budget is a decision about advisory checks only.

Step 4 — Activate on your machine two invocations

Activation is a command. The first invocation previews exactly what the transaction would change and writes nothing; the second performs that exact preview:

1 — Preview, and read it

node .agents/skills/change-evaluation-gate/scripts/gate.mjs activate

2 — Confirm that exact preview

node .agents/skills/change-evaluation-gate/scripts/gate.mjs activate --confirm PASTE_THE_TOKEN_HERE

If the executable is on your path it is simply change-evaluation-gate activate. The path form is installation-specific: the script sits wherever your client placed the skill, so resolve it beside the skill's own SKILL.md rather than copying a path from here. Once this succeeds you never need either form again — activation writes a git gate shortcut into this clone's own .git/config, and every later command in this guide is git gate … from anywhere in the repository.

Activating a desktop client? Its hooks file must already exist

Plain git is the default and needs nothing. A desktop client is a separate, later invocation — gate activate --client cursor — and it registers the Gate by merging one entry into a file that client owns. The Gate never creates that file. It cannot know a format it has not read, including whether the format carries its own version, so a missing file is reported rather than invented: 

adapter-registration-unverified
The declared registration file .cursor/hooks.json is not on disk.

Activation still succeeds — that client is simply left unregistered and sends you no preflight. Create the file yourself first, then activate:

A minimum Cursor file, if you have none

mkdir -p .cursor
printf '{\n  "version": 1,\n  "hooks": {}\n}\n' > .cursor/hooks.json

Everything else in that file is written back exactly as its owner wrote it — other hooks, other events, the permissions block beside one client's hooks. If something other than the expected container already sits where the entry belongs, the Gate reports surface-shape-incompatible and leaves the file untouched rather than repairing it.

A desktop client can pause the transaction

Trust is granted by the client, never by the Gate on your behalf. A desktop client that has not granted it pauses activation, leaves no integration active, and prints the exact command that resumes it — gate activate --resume <transaction-id> --confirm <token>. Grant trust in the client, then run that.

The token binds the confirmation to that exact preview

Exactly like the migration confirmation in Step 2. If your configuration changes between the two invocations, the token stops matching and nothing is written. Note also what the receipt can honestly record: the command cannot see who typed the confirmation, so --actor is stored as self-declared and never as proven.

Activation runs as one transaction, in a fixed order, and enables Git last:

  1. repository-identity — confirm which clone this is
  2. preview — show the exact changes and commands
  3. consent — you approve that specific preview
  4. runner-resolution — resolve each command to a real executable
  5. trust — client-controlled, never granted on your behalf
  6. hook-chain-validation — inspect existing hooks without touching them
  7. self-test — prove the machinery works before relying on it
  8. receipt — record what was pinned
  9. git-enablement — only now can a commit be blocked

If any step fails, everything already done is unwound and your clone is left configured — never half-activated. Existing hooks are never overwritten: the Gate composes into a hook chain, or refuses and tells you why.

Section 10

What happens at a commit

You run git commit. Before Git accepts it:

  1. The Gate materialises an isolated snapshot of exactly what you are committing.
  2. It resolves which checks apply, in ladder order.
  3. It runs them against the snapshot, never against your live files.
  4. It applies your policy: required failures and unverifieds deny; advisory ones do not.
  5. It writes an evidence record and returns a decision.

A denial tells you which check failed and why, without you having to dig through logs. That explanation is also written to the clone-local evidence record, so it is still there after the terminal has scrolled. If the record cannot be written, the commit is refused — a decision with nothing to point at afterwards is not an authorisation.

Your working directory is never modified by an evaluation — checks that would rewrite your code are rejected at commit time and belong to a separate explicit fix operation.

If you genuinely need to commit anyway

Bypass is optional — a project can disable it entirely. Where it is enabled it is deliberately awkward: one-shot, bound to that exact snapshot, requires a written reason and any reference your policy demands, and emits a commit-visible marker. It returns bypassed, never passed, and the failures it stepped over stay recorded.

It is granted by a command, never by a flag on git commit. When a commit is denied on a clone whose policy enables bypass, the hook says so and names the command: gate bypass --reason "why this one commit may proceed" previews the exact staged snapshot the grant would bind to and prints a token; run it again with --confirm <token> to write the grant, then commit. The grant is spent by that next commit whether it applied or not; stage anything else first and it is refused as snapshot-mismatch. The hook prints the configured marker for you to put in the commit message — it runs before a message exists and cannot write it for you. With bypass disabled, gate bypass refuses and nothing else changes.

Evidence limits

Records are bounded so they cannot fill your disk: 32 KiB inline per attempt, 4 MiB per output blob, 32 MiB of blobs per evaluation. Projects may lower these, never raise them. Truncation keeps the beginning and end of output and records how much was dropped. Nothing is ever deleted automatically — pruning is manual and preview-bound.

Section 11

Everyday commands

On an activated clone every one of these is git gate …. That shortcut is a clone-local Git alias activation wrote into this clone's own .git/config and nowhere else — it works from any subdirectory, it is never committed, and it never follows the repository to anybody else. Deactivating leaves it in place, so a deactivate/activate pair runs through it end to end.

The one you will run most

git gate status

It ends with one next: line naming the command that recovers what it found — git gate repair for a moved Git hook, git gate sync for a changed policy, nothing on a healthy clone. It names the command; it never runs it. A denied commit, a Cursor follow-up, and a git gate repair with nothing to restore name their recovery from the same table, so whichever one you read first names the command that actually recovers the clone — and says that your configuration and all historical evidence survive it.

Every command follows one rule: it previews and writes nothing until you run it again naming the token the preview printed. No flag previews and performs in one invocation, and there is no --yes or --force. 

git gate repair                          # prints a preview and a token
git gate repair --confirm <token>        # performs exactly that preview

Add --json to any of them for the same document in machine-readable form. Exit status is 0 when nothing is wrong or the confirmation was performed, 1 when the clone needs attention — including a confirmation this clone refused — and 2 when the command could not run.

OperationWhat it does
statusReports healthy, degraded, or broken, checking everything the receipt pinned — your configuration included — exactly as the next commit will. Ends with a next: line. Repairs nothing and writes nothing — observation never mutates.
repairRestores drifted Gate-owned Git hook registrations to what the receipt already pinned. It covers three findings and nothing else — hook-absent, hook-block-tampered, hook-receipt-mismatch. Everything else is reported as unrepairable: a lost desktop client is a reinstall, and a changed policy is Section 12. With nothing to restore, its next: line names what does recover the clone.
syncRe-pins a changed .agent-framework.yaml under the adapters this clone already has, keeping every registration byte for byte. Its preview says whether the new policy is weaker than the one it replaces. Section 12.
updateSwitches to a newer Gate release atomically. Installing a newer version only makes a candidate available; nothing changes until you update deliberately. It does not re-pin your policy — see Section 12.
bypassGrants one one-shot bypass of the exact staged snapshot, where policy enables it. Section 10 covers what it demands.
deactivateRemoves the hook and receipt. Keeps your configuration and all historical evidence.
uninstallRemoves project-installed assets. Requires deactivation first.
cleanupRemoves only Gate keys from .agent-framework.yaml. Never deletes the file.
pruneRemoves evidence output blobs you selected by evaluation, age, or reclaimed size. Envelopes, decisions, events, and a tombstone for every removed blob are always kept.
locksInspects the coordination lock. Reports a free lock, a live holder, or a stale one; recovers a stale holder only against its own token, and never takes a live one. Coordination is built and not switched on: no evaluation acquires this lock today, so it reports free unless something else wrote it.

Every removal is conservative: it touches only unchanged Gate-owned state, and refuses the whole operation rather than half-doing it. Anything that drifted is reported and left exactly where it is.

Two things this command is not

gate fix is a separate contract and is refused here by name — an evaluation never rewrites your code, so applying a formatter's rewrite is its own explicit operation. And there is no subcommand that evaluates the tree on demand: to find out what the Gate thinks of your work right now, commit, or read the preflight your desktop client sends.

Section 12

Changing policy after activation

This is the part that surprises people, so it gets its own section. Editing .agent-framework.yaml on an activated clone does not change what the Gate enforces. Activation pinned an identity of that file into the receipt, and the next commit compares the file against that pin.

What actually happens after you edit the file

The next commit is denied. Not with a verdict about your code — the control surface no longer matches what the receipt pinned, so the evaluation is unverified with integrity-drift. The clone cannot say what it is enforcing, and nothing that cannot be said is proved.

git gate status sees it first. It makes the same observation the commit makes, so it reports broken with a control-surface-drift finding on trusted-configuration that names .agent-framework.yaml, and its next: line names the re-pin below. Status and the commit agree: when one says drifted, so does the other. The denial itself ends Next: git gate sync — … for a changed policy, a changed check command, or a pinned runner that moved, and names git gate repair only when what drifted is the Gate's own hook.

Re-pin the changed policy — edit, then one preview and one confirmation

git gate sync                            # what the policy was, what it is now, and whether it is weaker
git gate sync --confirm <token>          # pins exactly that preview

The preview names the identity the receipt pinned, the identity your edited file produces, the adapters it keeps, and the commands it will pin. Confirming it rewrites the receipt and nothing else: the hook and every desktop client's registration stay byte for byte as they are, and git gate status reports healthy again. If anything fails on the way, the old receipt is put back exactly and the clone is as it was.

A weaker policy is refused until you say you mean it

If your edit demotes a required check to advisory, or stops binding it at all, the preview heads its findings WEAKER than the trusted policy, names each one, and prints no token. To pin it anyway, preview again with the acknowledgement and confirm that preview: 

git gate sync --acknowledge-weakening
git gate sync --acknowledge-weakening --confirm <token>

The token binds the new policy and your acknowledgement together, so the same token without the flag, or after another edit, pins nothing. Only a demoted or removed required check counts as weaker today; a looser budget or an enabled bypass does not.

The weaker-or-not judgement needs the policy you are moving away from, not just its identity. git gate sync reads it from the receipt when a previous sync wrote it, and otherwise from the committed .agent-framework.yaml at HEAD. If neither reproduces what the receipt pinned — you committed past the Gate, say — sync refuses rather than guess, and names the older route.

Adding or removing a desktop client is still git gate deactivate then git gate activate, each previewed and confirmed. Sync keeps the adapter set the receipt pins, and says so and names that pair when the installed Gate declares a different one. Deactivation keeps your configuration, every historical evidence record, and the git gate alias.

The preview identifies the bytes on disk, not the buffer in your editor. An unsaved change produces a sync with nothing to sync and a candidate identity that looks unchanged — which reads exactly like the tool ignoring you. If the identity does not move after an edit you believe you made, the edit is not on disk.

Configuration itself is one-shot: running --configure-gate a second time fails with The Gate is already configured. After the first time you edit the evaluation_gate block in .agent-framework.yaml directly, or remove it with git gate cleanup and configure again.

Section 13

When the Gate disagrees with your terminal

A check passes when you run it by hand and fails or reports unverified under the Gate. Almost always this is the evaluation environment, not your code. Work down this list in order — it is ordered by how often each one turns out to be the answer.

When the Gate cannot supply something a check declared it needs, it says so by name and never dresses that up as a verdict about your code — so treat unverified as a message about the environment until you have ruled the environment out.

Section 14

Limits you should know

These are real constraints in 0.8.0, not disclaimers. Plan around them.

It is not tamper-proof

Trust boundary

The Gate is a cooperative local process running with your own permissions. Anyone can pass --no-verify, delete the hook, or edit the evidence files. It does not resist the machine owner and is not a sandbox. It is reproducible pre-commit enforcement for a trusted developer machine — not a substitute for CI, and not protection against hostile code.

Desktop client support is narrow

Desktop editors can show preflight feedback before you commit, but they never authorise anything — only the Git integration does. Support is claimed only where a real client has actually been tested:

SurfaceStatusWhy
Cursor 3.15.6supportedPassed the full baseline driven by a real client invocation.
Claude Code DesktopexperimentalNo client-driven baseline run yet.
Codex DesktopexperimentalNo client-driven baseline run yet.
GitexperimentalAuthoritative regardless of tier; tier reflects baseline provenance.

After you activate, Cursor may send a follow-up when a required check fails on the work in front of the agent. A clean turn is left alone. That message is not the decision a commit would receive: preflight grades the working tree, including unstaged edits; git commit still grades the isolated snapshot. Claude Code Desktop and Codex Desktop do not currently send a follow-up — they have no declared channel to answer through — so silence from those clients is not a pass.

The follow-up carries the whole decision, not just its failing checks: the outcome, each failing check's own summary, every diagnostic by reason code, and every Grader surface the work edited. A clone whose checks all pass but whose Gate has drifted says so: 

Preflight (not a commit decision): unverified.
Diagnostics:
- integrity-drift: The Gate control surface drifted independently of this change (trusted-configuration); nothing here is proved. Next: git gate sync — a new Activation transaction that re-pins the configuration …
- dependency-root-unavailable: The declared dependency root "vendor" could not be provided to this evaluation; …
Changed Grader surfaces (this change edits what grades it; stated for visibility):
- gate-configuration .agent-framework.yaml

Read integrity-drift and dependency-root-unavailable as messages about the clone and its environment, not about your code: the drift line names the command that recovers it, a missing dependency root is cleared by installing it, and editing code clears neither. A changed Grader surface is stated even on a turn that passed, because editing what grades a change is worth a second pair of eyes; it is an observation, never an accusation. The message lists at most eight failing checks and eight other diagnostics, cuts any entry past 400 characters with …, and says what it left out by count and reason code. Drift and changed Grader surfaces are never left out.

The snapshot is not your terminal

Checks run against a materialized copy in a temporary directory, not your working tree. That copy has no .git, holds nothing your .gitignore excludes, and gets only the dependency roots you declared. A commit's copy holds the tracked content being committed; a preflight's also holds every untracked file you have not ignored (Section 09). A command that expects any of those finds them missing. When a check declares what it needs and the snapshot cannot supply it, the Gate reports unverified naming the unmet requirement — never a verdict about your code. Treat that as a message about the evaluation environment, and do not change your project to satisfy it.

One environment is claimed

The release records exactly one tested environment: macOS 26.6.1, arm64, Node v24.6.0, git 2.51.0. Every other combination is unverified — not refused. Running the portability matrix on another machine is how that machine earns a claim. This is deliberate: tested versions are an evidence snapshot, never a permanent allowlist.

Some things you have to find out by doing them

There is no command that reports what this machine can do before you commit to anything, and no command that evaluates the tree on demand. You learn that a runner does not resolve here when an activation preview refuses, and that a check fails when a commit is denied.

Two risks stay open

  • Slow checks encourage bypass. If your required checks are slow, people route around them. Keep the commit gate fast and put slow suites in CI.
  • Flaky checks block delivery. Two runs of one unchanged check that disagree produce unverified and block, by design. Fix the flake rather than retrying it away.
